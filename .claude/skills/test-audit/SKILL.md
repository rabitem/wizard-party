# Test audit

Every test must protect something a player, an operator or another module can observe. This skill
is the gate for new and changed tests and the method for pruning existing ones.

- Writing or changing a test: run the [authoring gate](#authoring-gate) and pick the boundary from
  [boundaries.md](references/boundaries.md).
- Reviewing or pruning tests: read [audit.md](references/audit.md) first.
- Pruning a whole area (for example `party/` or `components/three/`): also read
  [CAMPAIGN.md](CAMPAIGN.md).

## Authoring gate

Answer all four before adding a test. If an answer is "no" or "I don't know", don't write it.

1. **What observable behaviour, invariant or contract does it protect?** Name it in the test name.
   "Tied players all win the game", not "calls rankPlayers".
2. **Which credible regression makes it fail?** If you cannot describe a plausible code change
   that turns it red, the test proves nothing.
3. **Why does existing proof miss it?** Each contract has one primary owner at the strongest
   boundary that can see it. A second layer needs a distinct risk (transport, persistence,
   timing, rendering), not the same assertion replayed. Extend the owner's table or fixture
   before adding a new file.
4. **Does it need an export, flag, wrapper or hook that production never calls?** Then the test is
   at the wrong boundary. Move it to the real entry point.

Rules that follow from the gate:

- A bug fix gets one regression test at the owner of the bug. It must fail before the fix for the
  intended reason. Don't replay the same bug at every layer it crossed.
- A behaviour-preserving refactor must not break any test. If it does, that test was coupled to
  the implementation: fix the test, not the refactor.
- Expected values come from the rules or the spec, never from running the subject.
- Determinism is required: seeded randomness (`shared/application/ports` random port,
  `src/infrastructure/sandbox/seeded-random.ts`), fake or virtual clocks, no real network.

## Junk patterns (reject in review, delete in audits)

- No assertion, or an assertion that cannot fail (self-comparison, `expect(x).toBeDefined()` on a
  constant, a snapshot of a value the test built itself).
- Expected values generated by the code under test.
- Copied inventories: lists of exports, config keys, scenario names or file names that only
  repeat the source.
- Source or string greps that break on a rename but not on a behaviour change.
- Call-shape assertions (`toHaveBeenCalledWith` on an internal collaborator) where the observable
  result could be asserted instead.
- Mocks that implement the behaviour being asserted, or pretend two different APIs match.
- Fixtures that fabricate what the owner should produce: server events, acknowledgements, command
  order, stored state the code never writes.
- Negative tests that pass because of an unrelated guard, or test a rejection production never
  reaches.
- Names that promise behaviour the inputs never exercise.
- Test-only exports, globals, `__forTesting` hooks or reset functions with no production caller.

## Retention bar (never delete for being slow or static)

Keep independent proof of:

- the wire protocol (`shared/domain/events`, `party/protocol`), protocol-version compatibility and
  close codes;
- game rules and scoring (`shared/domain/expansions`), including hidden-information rules;
- persistence and migrations (`db/`, room storage, restart recovery);
- security boundaries: auth, session tokens, rate limits, input decoding, what each player may see;
- reconnect, pause and timeout behaviour, and observable event ordering;
- public config defaults and storage keys players' browsers already hold;
- architecture rules the linter cannot express.

A baseline failure may be a product bug. Reproduce and fix it at its owner; never delete the test
to make CI green.

## Proof and hand-off

- Run the owner's tests and its siblings: `npx vitest run <paths>`. Where your machine cannot run
  them, push and read the CI run (`.github/workflows/ci.yml`). Say which you did.
- Browser suites cost runner hours. Use `workflow_dispatch` on `e2e.yml` with a narrow `grep`, not
  the `e2e` label, unless the change is about rendering, input or layout.
- Report: contracts kept and where they live now, what was deleted and why, production lines
  versus test lines changed, and anything left unproven.
